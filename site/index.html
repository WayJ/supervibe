01 / WORKFLOW

把迭代，变成可追踪的闭环。

不是另造一个调度器。
用六个 Skills，连接规划、执行与交付。

01supervibe:roadmap

先定义“完成”

创建 Epic，拆分 Sprint，制定共同 DoD，以及 Sprint 和整体 Roadmap 各自的验收场景。

02supervibe:start

有条件地启动

预留 WIP，再创建 Sprint 文档与 worktree；登记跨 Sprint 的后续复核义务。

03supervibe:accept

证据先于结论

按场景执行验收，检查文档漂移，用新鲜证据对当前候选版本作出裁定。

04supervibe:complete

合并不是最后一步

从门禁和裁定复核，到合并、账本、worktree 清理、交接条款与收尾记录。

05supervibe:sync

让并行持续对齐

将 origin/main 合入进行中的 Sprint，检查已触发的交接条款，保留同步记录。

06supervibe:board

看清全局

生成本地只读看板，呈现 Epic、Sprint 与交接条款。它是生成时快照，不是实时账本。

reserved→active→acceptance→merged→closed

02 / COLLABORATION

两种编排路径。
同一套交付契约。

协调者就是当前主 Agent。
不额外启动一个“协调 Agent”。

⌘

NATIVE / HARNESS

用宿主原生的协作能力

例如 Claude Code 的 subagents。复用当前 harness 已提供的 worker 工具与执行能力，而不是发明一套通用 spawn API。

适合同一 harness 内的任务分工
⇄

EXTERNAL / ORCA

把协作延伸到会话之外

通过 Orca CLI 委派跨会话、跨 harness 的工作。启动迭代时确认 worker harness 类型；混用 harness 需要明确许可。

适合跨会话 / 跨 harness 的任务分工
启动时，一次说清楚。

确认编排模式、worker 并发上限、适用的 harness，以及是否设置独立验收 worker。策略存入本地共享账本，恢复时复用；缺少能力时阻塞，不静默降级。

maxWorkers: 1 = 主 Agent + 一个 worker，不是单 Agent。明确选择不使用 subagent 时，直接进入 superpowers，不初始化迭代模式。

03 / GUARDRAILS

并行提速，不把风险并行放大。

A / ACCEPTANCE

CI 绿了，不等于用户能用了。

Sprint 制定时就写明验收要求；Roadmap 还需要独立的整体集成验收。UI 场景必须包含真实浏览器操作、观察结果和证据，不能用 API 测试冒充。

  • 必需场景失败、未运行或被替代，都阻塞验收。
  • 可选独立验收 worker，身份与开发 worker 区分。
  • 每次唤醒 / 恢复，重查环境、工具、账号、数据和证据采集条件。
B / RESOURCES

隔离了代码，还要协调运行资源。

先评估电脑的 CPU、内存、磁盘与工作负载，再确认预算。worker 数量、Sprint WIP 和环境容量是三个不同限制。

  • 容器、端口、数据库、浏览器配置和测试账号通过资源组协调独占使用。
  • 资源使用权不等于重启、重置或改密码的权限。
  • 可登记 SSH 云服务器作为资源环境；不会自动连接、安装或配置远端。

LOCAL BY DESIGN

worktree 各自开发，账本共享一份。

同一 clone 下的 worktrees 共享 Git common-dir 中的运行状态。分支上的 Markdown 保存规划、验收证据和可读投影，但不能代替账本授权启动或合并。

明确验证边界，比“看起来能用”更重要。

协议与 fixture 测试不等于真实后端验收。原生编排 / Orca 的实际端到端运行尚未验证；真实浏览器证据、后端容量与 SSH 环境仍需现场核验。资源账本是协作协议，不是操作系统沙箱。

04 / GET STARTED

从下一个迭代开始。

在 Claude Code 中安装插件，然后从 Roadmap 明确目标、验收与协作策略。

脚本运行需要 Node.js ≥ 20。项目零 npm 依赖。
建议搭配 superpowers；未安装时仍可手动产出同样的 Markdown 契约。
